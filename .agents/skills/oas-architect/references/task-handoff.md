# 开发任务合同与执行者接力 V1.2

## 角色与普通恢复

代码实施者和交接文档维护者按本文件工作，Codex 负责合同与最终审查。普通恢复先取得 Git 和 CURRENT，预算采用提醒并继续补齐必要事实。正式验收按明确对象触发，范围见 [review-closeout](review-closeout.md)。

## 同一份合同用于所有执行者

开发统一由获授权的执行者实施，不绑定模型或客户端；Codex 负责合同、开发结果的源码审查、必要的最小测试和最终验收。用户授权 Codex 直接实施时仍须单列自审与验证，不能称为外部独立审查。
不猜订阅额度，不因存在 CLI 路径就认定账户、工作区或模型可用。启动 CLI、跨环境传输和写入须在现有授权内。
V1 使用人工或已有授权通道交接，不建设后台调度、并行 Agent 协商、额度探测或其他厂商适配。

## READONLY-V1 严格只读审计模式

仅合同标记 `execution_mode: readonly_audit` 时采用；正常已授权开发仍可在合同范围内修改代码，不更改执行者客户端的全局权限。

- 启动前核对本机 CLI 版本及帮助，显式仅提供 Read、Glob、Grep；禁用写入、代码执行、hooks、MCP 及其他可改变状态的通道。不能只靠提示词；无法核实实际工具集合或审计不完整时报 BLOCKED／PARTIAL。
- 不使用可能写内部计划的 Plan Mode；在本机支持时采用拒绝未预批工具的非计划模式，并将工具清单与允许规则限制为三种读取工具。临时配置／运行材料在仓库外，不能改用户全局配置或借只读审计扩大目录访问范围。
- Read／Glob／Grep 之外的调用、Write／Edit／NotebookEdit／Bash、内部计划写入或任何间接写入尝试均违规；即使被权限拒绝也判 FAIL。直接在最终回答中给结果，不创建计划、报告或测试文件。
- 分开记录“硬性工具限制生效”和“模型没有写入尝试”；保存启动参数、实际工具集合、完整调用／结果配对、退出码及前后文件 SHA-256。CLI 退出0和理解正确不能替代行为验收。

## 标准任务合同

先把目标、触发、预期行为、既有功能与配置保留、修改范围、验证和风险问清，形成具体方案并取得用户对该方案的明确同意，再交接或实施；同一已批准方案内不重复审批，超范围或需求变化先确认并审核。

以下是结构规范，实例内容用中文填写。CURRENT 保存任务摘要、合同版本、批准范围、验收条件和有效合同链接；长方案可指向可访问且带版本／指纹的材料，不能只依赖聊天历史。

```markdown
# OAS 开发任务合同

- task_id：
- contract_version：

## 1. 任务目标（Task Objective）
问题、期望行为与完成边界。

## 2. 项目上下文（Project Context）
worktree、内容基线、相关模块与必要资料。

## 3. 批准架构（Approved Architecture）
批准方案、有效 ADR、不变量和批准来源。

## 4. 修改范围（Modification Scope）
允许操作、模块／文件、预期新文件、共享文件处理办法。

## 5. 约束（Constraints）
禁止事项、兼容性、预存 WIP、设备与 Git 限制。

## 6. 实施步骤（Implementation Steps）
顺序、依赖、阶段边界和停止条件。

## 7. 测试要求（Testing Requirements）

收口原则：仅审查本次增量及直接调用方，验证批准行为和直接回归风险；默认不新增测试文件或复杂替身，优先复用最小现有用例。发现范围外缺陷只记录并报告，不顺带修复、重构或扩大验证；确需扩大修改范围先交用户确认。最小检查满足后停止离线扩测，交付待实测版本。
默认列1～3个能区分对错的关键场景、原图/日志或最短已授权实测。普通任务阶段离线测试累计120秒，包含实施、复修与Codex复核，不因拆组/交接重置；交付已用时间、剩余预算、命令/日志与内容指纹，缺失时先核对已有记录，不另起完整预算。复用未受影响证据，不机械重复整组。无实机授权时尽早交付待实测版本与最短步骤；扩大范围/预算及全量须明确批准。

## 8. 验收标准（Acceptance Criteria）
可核查的需求、代码、证据与阶段条件。

## 9. 报告（Reporting）
修改文件与增量、设计偏差、实际命令与快照、通过／失败／跳过／未执行、证据、未解决问题、diff 摘要。
```

普通范围内的实现细节不要求反复审批；核心架构、L1 点击管线、双实例同步核心、跨模块重构和范围扩大必须取得用户批准。
文件范围可采用明确模块与预计文件，但不能因此覆盖共享文件中的其他主题。执行者不得自行改变已批准架构。
执行者遇到阻断性设计冲突时暂停受影响修改并报告；可独立完成的已授权部分不必全部停下。

## 预存 WIP 与任务增量

- H：HEAD；B：本任务开始时工作区内容；C：当前检查点内容。
- H→B 是预存修改，B→C 是任务期间变化；有外部写入时 B→C 也不能直接证明作者。
- 开始前记录分支、HEAD、实际 worktree／公共 Git 目录、暂存与未暂存清单、全部未跟踪文件。
- 对任务会触及的既有文件保存 B 的可比较内容；对其他受保护变化记录清单和指纹，必要时保存全部变更文件快照。
- 保留二进制资源、未跟踪模块及依赖；仅普通 `git diff`、HEAD 或哈希都不足以还原完整 dirty 工作区。
- 哈希发现变化，开始内容用于比较；两者都不能自动证明归属。无法判断时标记共享／来源不明并保护，不自动回滚。
- 内部基线材料放 `D:\Codex\workspace` 的独立目录，用户交付物默认放 `D:\Codex\outputs`；不覆盖同名旧材料，不复制整个仓库替代必要快照。
- 禁止未经授权的 reset、restore、clean、stash、checkout、删除未跟踪文件、暂存、提交、推送及整文件覆盖。

## 执行者中断后接管

1. 取得旧执行者已停止写入的可靠确认；文件暂时未变不等于执行者已停，未知时仅做只读检查。
2. 核实实际 worktree、分支、HEAD、Git 状态和合同版本。
3. 比较 B、当前源码、相关测试、资源与最后报告，不把报告当作实际代码或测试证据。
4. 区分已完成、部分完成、待修正、未开始和无法确认项，保留预存与共享 WIP。
5. Codex 核对 CURRENT 检查点后更新，形成同一合同下带版本的剩余任务，不把原任务整份重新执行。
6. 在批准范围内接管；范围、架构或验收条件变化时先更新方案并取得必要批准。
7. 对最终组合重新进行 [独立验收](review-closeout.md)。

非控制会话的执行者只提供结构化实施报告，不直接写 CURRENT；Codex 不以接管为由自动重启服务、删除运行记录或提高测试上限。

## 跨 worktree 或机器

先核实相关基准内容是否一致，再交接合同、基线标识、本任务增量、未跟踪依赖、资源、证据与未完成事项。
同 HEAD 不证明内容等价；绝对路径不可达时必须迁移必要材料并核对指纹，不能只改 CURRENT 的路径后宣称等价。
接收端出现重叠修改、文件缺失或基准不符时停止受影响应用并报告，不切分支、不强行覆盖、不假定共享工作区。
单任务不代表只有一个窗口；保持一个指定写入者，不为 V1 引入并行调度或第二份状态文件。

## 有效检查点

任务确定、方案批准、阶段完成、验证完成或失败、执行者切换、阻塞和对话结束时记录。
每个检查点至少有合同版本、内容基线／当前指纹、实施／验证／验收状态、执行者、风险与下一步。
完成后保留终态，用户未授权的下一阶段不得自动启动。
