# 审查、严格验收与任务收尾 V1.2

## 触发和对象

用户要求审查、验收或执行指定验收合同后，确认目标、对应内容版本、完成标准及证据范围。普通恢复按 [context-loading](context-loading.md) 取得任务状态，预算提醒后继续必要读取。

代码审查核批准需求、实际源码、开始到当前的差异和验证。上下文读取验收另按其合同审计原始工具调用。自审注明实施者和审查方式，独立会话或审查者注明来源。结果采用 PASS、FAIL、BLOCKED、NOT_TESTED，关联具体范围。

## 五层验收

| 层次 | 核对事项 |
|---|---|
| 需求 | 用户问题、批准目标、边界与验收条件是否满足；有无遗漏或额外行为 |
| 架构 | 当前调用链、批准方案和有效 ADR；模块边界、复用、兼容与其他业务影响 |
| 代码 | 实际源码和 B→C 增量、异常、状态流、共享文件、资源与未跟踪依赖；不把 H→C 全归入任务 |
| 测试 | 真实命令、环境、快照、完整输出、退出码、skip、未执行项及证据有效性 |
| 文档 | 六份核心 MD 逐一判断项目事实是否改变；CURRENT 的任务状态、合同和接力是否准确 |

Codex 自己实施时也单独进入 `reviewing`，从批准合同、原始规范和 diff 重新核对，不以实施过程代替证据。
可用新对话减少偏差，但不声称同一 Agent 自审等同于完全独立的外部审计；最终责任仍由 Codex 承担。

## 证据与快照

每条验证记录至少包含命令、时间、工作目录、范围、输入内容快照标识、通过／失败／跳过／未执行、退出码与输出位置。
有条件时记录相关文件哈希及日志指纹；HEAD 和“运行成功”一句话不足以绑定长期 dirty 工作区。
相关源码、测试、配置或资源变化后，受影响旧证据标记过期；未受影响的证据可保留，不为刷绿重复运行。
哈希不匹配、材料不可达或无法证明对应版本时报告不确定，不能伪造通过。
执行者报告是线索，不是唯一依据；测试文件存在不等于通过，mock／静态截图不等于连续游戏流程。

## 验证范围

纯 Skill／文档变更：frontmatter、结构、references 与文档链接、CURRENT 字段、入口共同规则、忽略规则、增量 diff、编码和 WIP 保护等静态检查即可。
静态脚本不是业务 unittest，不为这种变更机械运行 OAS 全量、compileall 或启动服务；客户端发现、恢复与协作演练必须另有授权。
业务源码按[TESTING §1](../../../../docs/TESTING.md)选择最小相关检查，普通局部默认120秒。全量只在用户或已批准合同明确包含该次运行时执行，未运行全量不阻塞普通局部交付；不要把下方全量示例当默认步骤。已有明确授权直接沿用，分组/获准全量仍走守护。

```text
toolkit/python.exe dev_tools/guarded_unittest.py --timeout-s 120 -- tests.<模块>.<类>.<方法>
# 仅明确批准该次全量时：
toolkit/python.exe dev_tools/guarded_unittest.py --profile full -- discover -s tests
```

守护超限只停止并报告，不自动重跑或提高上限；14（已有运行）／16（清理失败）先按摘要核对 PID、创建时间和命令行，不删记录绕过。
不启动 MuMu、游戏、真实 ADB 或 OCR；Level C 沿用 TESTING §2 的限制，不把离线通过宣称为设备验证。
既有失败、skip 和空白问题单独报告；不为变绿改无关业务，也不把后来一次通过当作历史失败根因已解决。

## 文档同步

| 文档 | 事实变化时处理 |
|---|---|
| AI_CONTEXT | 当前能力、入口、限制和验证摘要；历史不能无限追加为多个“当前” |
| DEVELOP_LOG | 实际项目变更后追加，不覆盖旧历史 |
| ROADMAP | 任务、阶段、依赖和验收队列；后续计划不写成完成 |
| ARCHITECTURE | 仅真实分层、核心链或公共契约变化；纯开发流程可无需修改 |
| DECISIONS | 新的长期项目决定或明确替代关系；不抹除旧 ADR |
| TESTING | 长期验证流程、证据规则或分级变化 |

CURRENT 单独维护当前任务，不把它扩成项目总历史。六份全部保留，不机械更新、不自动精简、合并或归档。
新增说明用中文；角色路由可不同，共同核心规则不得互相冲突。规则变化按事实同步相关入口与文档，不创建循环加载。

## 完成状态与停止点

- 实施完成：批准范围内的内容已落地。
- 验证完成：对应快照取得所要求的实际证据；跳过／未执行必须单列。
- 验收完成：满足批准的全部完成条件并有 Codex 审查结论。
- 三者独立。前端未实现、真机未验或协作演练未做时，不能以其他范围通过替代。
- 未授权后续阶段：CURRENT 保留 `awaiting_approval` 与待验收项，不把整任务写成 `completed`。
- 已 completed／cancelled 的任务不自动重复执行，只有用户明确新目标或重新打开才进入实施。

## V1.1 严格协议兼容

历史 T12 按当时合同保留结论。其 Unicode 预算为 L0/L1/L2 软 12000/9600/4000、硬 15000/12000/5000，总软 25600/硬 32000，单次目标 6000/硬 8000，每次至少 640 包装预留。完整返回包含发现、错误、警告和包装，按 call_id 配对，custom 文本块间单 LF，function 字符串片段直接拼接。未知、缺失、重复或截断保留。

旧协议的 raw 源 SHA、最终 LF 正文 SHA、范围、BEGIN/BODY/END 与缓存实收校验继续按对应历史快照审查，空匹配及未执行项如实记录。精确读取量采用会后原始 JSONL 外审。

旧实现保存在 scripts/oas_strict.py。使用旧模式必须显式带 --strict，例如 `toolkit/python.exe -B -X utf8 .agents/skills/oas-architect/scripts/oas_context.py verify --strict`。这是 V1.1/T12 专用兼容工具，entry/knowledge 的历史字段与固定读取目标仅适用于其原合同快照。新验收按当前目标选择证据，旧结果与新普通恢复分别记录。

## 收尾报告

核对 git diff／status、原有文件指纹与任务增量，说明工作区保护、实际新增／修改、验证证据、CURRENT 三个状态、未完成项和下一阶段边界。
报告必须保留固定“文档同步”段，六份逐一写已更新／无需更新及原因。
不自动暂存、提交、推送、清理或开始下一阶段；生成交付物默认放 `D:\Codex\outputs` 的独立任务目录。
