# 三案例 Verify / Wait / Retry / Recovery 架构归纳

> 2026-09-02。基于三个已完成迁移前静态收口 + characterization 的真实案例
> （`BaseTask.list_find` §4.19、Kekkai §4.33 / `docs/Kekkai状态机静态收口.md`、
> RealmRaid §4.34 / `docs/RealmRaid状态机静态收口.md`）横向归纳，判断 Verify / Wait /
> Retry / Recovery 四类职责的边界与公共化程度。
> **本轮不修改任何业务生产行为，不新增任何 Python 代码**（结论见 §16 / §17）。
> 事实基准：HEAD `2cdf3a05` + 当前工作树，逐行重新核实 `tasks/base_task.py` /
> `tasks/{KekkaiActivation,KekkaiUtilize,RealmRaid}/` / `module/base/frame_wait.py` /
> `module/atom/frame_state.py` / `module/base/retry.py`。

## 1. 总结

**当前是否已经适合抽公共 Retry / Verify 层？→ PARTIAL，且不是现在。**

- **Structural wait**（`list_find` / Kekkai 列表 swipe）：**已经有** primitive
  ——`module/base/frame_wait.py::wait_for_changed_and_stable`，设计完整、无缺口。缺的
  100% 是 Level C 参数（ROI / 阈值 / `stable_frames` / timeout）+ 每个调用点的 baseline
  捕获与 action 包装。**不需要第二套 structural wait 抽象。**
- **Semantic verify**（RealmRaid `fire()` 的「旧标识消失」、未来「消失 + 战斗标识出现」、
  Kekkai `screening_card` 等标识消失）：**现有 primitive（`wait_until_appear` /
  `wait_until_disappear` / `appear`）已足以组合**，只差 `wait_until_disappear` 补一个
  `wait_time` 参数（1 行签名，但改 `fire()` 时序 → Level C）。**不需要新的 `Verifier` /
  `ActionVerifier` 类。**
- **Bounded retry**：三个案例的 action-retry 循环（`fire` / `fire_again` / `ensure_lock` /
  `check_refresh` / Kekkai `screening_card`）确实有共同骨架「locate → action → verify →
  bounded retry → return result」，**但**：① 每处的 action 每轮在 2~3 个 target 间交替，
  不是「retry same action」；② **当前全部无 bound**，加 bound 就改时序 → 每个消费者的接入
  都是 Level C；③ recovery 差异极大（`fire` 当前什么都不做且是死分支 / `ensure_lock` 直接
  往下走 / Kekkai `screening_card` → `_card_not_found` → `raise TaskEnd`）。**唯一真正
  共同的内核只有「计 attempts + 独立 total timeout + 返回 frozen result」约 15 行**——
  值得未来抽，但**不值得现在在零消费者下抽**（会变成又一个像 `frame_wait` 一样长期
  待接入的组件），应等第一个真实 Level C 迁移时对着真实消费者定形。
- **Recovery**：三个案例的失败后处理（`return False` / `refresh` / `switch group` /
  `failure record` / `goto_page` / `raise TaskEnd`）**高度业务特化**，必须留在 Task。

**下一阶段唯一推荐：Option 2 —— 先做一轮纯 Level A correctness / dead-code cleanup**
（§16 队列），理由见 §18。

**生产影响：零。** `list_find` / Kekkai / RealmRaid / GeneralBattle / FrameWait /
ClickSampler / ClickProfile / BehaviorTrace 全部未改。

## 3. Verify / Wait / Retry / Recovery 定义（基于本项目真实代码）

### Verify

> Action 执行后，确认**调用方期待的业务结果**是否真实成立。

- 不等同「页面发生变化」（那是 structural changed，是 FrameState 的语义）。
- 不等同「`sleep` 已结束」（那只是时间流逝）。
- 本项目里合格的 Verify 形态：`appear(ExpectedMarker)` / `not appear(OldMarker)` /
  `detect_page_in(page_battle)` / OCR 结果满足业务条件。
- **弱 Verify**：只检查「旧标识消失」（S2，见 §4）——旧标识消失有多种非成功原因。
- **隐式 Verify**：不写显式检查，靠「下一轮业务循环重新截图重新识别」自然收敛（S4）——
  在 `while` 有可靠退出条件 + 有 timeout 时可接受；无 timeout 时是缺口。

### Wait

> 在**有限时间窗口**内等待某个条件成立。只负责等待机制本身。

- 本项目现有实现：`wait_until_appear(target, wait_time=)` /
  `wait_until_disappear(target)`（**无 `wait_time` 参数**）/
  `wait_for_changed_and_stable(..., timeout=)`。
- Wait **不负责**：retry、recovery、refresh、`raise TaskEnd`、`goto_page`。
- 「有限」是硬要求：`frame_wait` 的 `timeout` 不允许 `None` / `inf`（D012）;
  `wait_until_appear` 不传 `wait_time` 时**退化成无限等**——这是当前 RealmRaid / Kekkai
  的一个系统性缺口，不是 Wait 概念本身的问题。

### Retry

> Verify 失败后，是否**再次执行某个 Action**。

- 必须有 `attempt bound`（最多执行 Action 几次）。
- 与「`while True` + `interval`」的区别：后者只有节流没有上界，Verify 与 Retry 揉在一个
  循环里，且没有「尝试次数」这个可观测量。
- 本项目现有 retry 机制：`module/base/retry.py` 的 `@retry` 装饰器——**异常触发式**
  （`try: f() except`），只用在 device / connection / adb / minitouch 等**基础设施层**，
  `tasks/` 内**零使用**。它的形态（catch exception + tries + backoff，无 verify callback /
  无 fresh screenshot / 无 result 对象 / 无 timeout）**不适配 task 层的 verify 触发式重试**。

### Recovery

> Retry 用尽 / 状态确认最终失败后，**业务层下一步做什么**。

- 本项目真实 Recovery 动作：`return False` / `refresh`（`check_refresh`）/ `continue` /
  `switch_friend_list`（换分组）/ `_record_utilize_failure`（计数 + 延迟 next_run）/
  `_finish_low_value_utilize` / `set_next_run` / `goto_page` / `raise TaskEnd` /
  `push_notify` / `find_one` 涂黑跳过。
- **高度业务相关**，且每个案例都不一样。这是「必须留在 Task」最强的一类。

## 4. Semantic Transition 模式

### S1 —— Action → 期望正向标识出现

```
State A ──Action──▶ 期望 State B ──▶ wait_until_appear(B_marker, wait_time=T)
```

真实 / 候选位置：

- RealmRaid `fire()` 未来：`click(partition)` → `wait_until_appear(I_FIRE, wait_time=T)`
  （当前**缺失**，只靠反复点）。
- RealmRaid `medal_fire()`（死代码）已经是这个形态：`wait_until_appear(self.I_FIRE)`。
- Kekkai `run_activation` A6：等 `I_A_INVITE` 出现（当前有等待，但 `while 1` 无 timeout）。

**最强**：正向标识只在「确实到达 B」时出现，误报概率低。

### S2 —— Action → 旧标识消失

```
State A ──Action──▶ wait / poll ──▶ not appear(A_marker) ──▶ 认定成功
```

真实位置：

- **RealmRaid `fire()`**：`not appear(self.I_RR_PERSON)` → `return True`（唯一判据）。
- **RealmRaid `fire_again()`**：`not appear(self.I_FIRE_AGAIN)` → `return True`。
- Kekkai `screening_card`：`not appear(self.I_A_EMPTY)` → 确认挂卡成功。
- Kekkai `ensure_lock` 反面：`appear_then_click` 直到旧态标识消失。

**为什么通常弱于正向 ExpectedState**：

1. 旧标识消失有多种非成功原因——弹窗遮挡其 ROI、页面切换动画中间帧、模板匹配在
   `threshold` 附近抖动、截图撕裂。
2. 单帧判否即认定，没有「连续 N 帧确认」。
3. 「A 不在」不蕴含「B 已到达」——中间可能是任意过渡态 / 加载页 / 报错弹窗。
4. RealmRaid `I_RR_PERSON` 的 ROI 在右侧边栏，恰是活动公告 / 好友邀请 / 体力提示这类
   浮层最常覆盖的位置。

### S3 —— Action → 旧标识消失 **且** 期望标识出现

```
State A ──Action──▶ not appear(A_marker) AND appear(B_marker)
```

候选：

- **RealmRaid `fire()` 的合理最终形态**：`not appear(I_RR_PERSON)` **且**
  `GameUi.detect_page_in(page_battle_prepare, page_battle)`（或某个战斗页正向标识）。
- Kekkai `run_utilize` U8：`appear(I_U_ENTER_REALM)` 后 `goto_page(page_friend_utilize)`
  ——已经接近 S3（有正向标识 + Navigator 两帧确认）。

**双条件把 S2 的四类误报几乎全消除**，是 RealmRaid `fire()` 迁移的推荐目标。**但需要
Level C 确认「过渡期是否存在同时满足两条件的帧」以及超时值。**

### S4 —— Action → 下一业务循环重新截图重新识别

```
while 1:
    screenshot()
    <判断当前局面并决定动作>
```

Kekkai 大量采用（`run_activation` 主循环、`screening_card` 三/四层、`check_utilize_add`）。

- **算不算有效 Verify**：当循环有**可靠的退出条件**（明确 `I_*` / 计数 / `Timer`）时，
  「下一轮重判」本身就是一种 Verify——它不断把当前帧与期望局面比对。Kekkai
  `_current_select_best` 的 `range(21)` + `Timer(120)` + `I_U_EMPTY_CARD` 三重退出就是
  合格的 S4。
- **只是隐式 Verify**：`check_utilize_add` 的 `count>=5` 退出——次数到了就走，并没有确认
  「这 5 轮到底成没成」。
- **缺口很大**：KA `run_activation` A6 / `screening_card` 的 `while 1` 无 timeout——
  「重判」永远在转，期望局面不出现就永不退出。

## 5. Structural Transition 模式

```
baseline（动作前帧）──Action──▶ changed（相对 baseline 出现过有效差异）──▶ stable（相邻帧连续安静）
```

三处真实 / 候选消费者：

| 位置 | Action | 当前「等停稳」 | swipe backend | baseline 可用帧 |
|---|---|---|---|---|
| `list_find` 翻页 | `self.device.swipe`（经 Control，**有 BehaviorTrace**） | `sleep(random.uniform(0.8, 1.3))` | `Control.swipe` → minitouch/adb | `self.device.image`（为识别而截） |
| KA `check_card_num` 翻页 | `self.device.swipe_adb`（**直连，绕过 Control / 无 trace**） | `time.sleep(1)` | 每轮 `while` 开头 `screenshot()` |
| KU `perform_swipe_action` | `self.device.swipe_adb`（**直连，绕过 Control / 无 trace**） | `time.sleep(2)` + `click_record_clear()` | 调用方下一轮 `screenshot()` |

**`module/base/frame_wait.py` 是否已完整覆盖这个 primitive**：**是。**
`wait_for_changed_and_stable(baseline, frame_provider, *, changed_threshold,
stable_threshold, stable_frames, timeout, roi=None, poll_interval=0.0, clock=,
sleeper=)` → `FrameWaitResult(frozen)`。它：

- 不自截（baseline 调用方传、当前帧靠注入的 `frame_provider`）；
- 所有阈值**必须显式传**，无业务默认；
- `timeout` 必须为正、超时不抛异常、返回 `timed_out=True` 的结果；
- 不做 retry / recovery / 换动作（D012 明确禁止）；
- 无 Device / BaseTask / Timer / BehaviorTrace 依赖。

**当前真正缺的**（全部是调用方 / Level C 侧，不是 primitive 自己缺）：

1. `baseline` 的**获取时机**——必须在 swipe **之前**截一帧显式传入（D013）。三个案例现在
   都只有「为识别而截」的帧，需要调用点新增「为等待基线而截」的语义或复用。
2. 真实 `roi`（列表可见区）、`changed_threshold` / `stable_threshold` / `stable_frames`
   ——Level C 采真实列表帧后标定。
3. `timeout` ——Level C 观察正常翻页耗时后定。
4. 调用方对「baseline 截图 + swipe + wait」整段的**包装形态**（D013 说这可能是一整个
   seam，边界收口阶段无法定稿）。

**结论：不再新增第二套 structural wait 抽象。** `frame_wait` 就位，等 Level C 参数 + 接入。

## 6. Retry 模式全量归纳

| RealmRaid `check_refresh()` 段 1 | `appear_then_click(I_FRESH, interval=1)` | `appear(I_FRESH_ENSURE)` | 是 | 是 | `RuleImage` 每帧重 match | **无** |
| RealmRaid `check_refresh()` 段 2 | `appear_then_click(I_FRESH_ENSURE, interval=1)` | `not appear(I_FRESH_ENSURE)` | 是 | 是 | `RuleImage` 每帧重 match | **无** |

## 7. 判断这些 Retry 到底是不是同一个东西

| # | 问题 | 答案 |
|---|---|---|
| 1 | Retry 的 Action 是否一样？ | **不一样。** `list_find`/Kekkai select-* 是「翻下一页」（search progression，每轮语义不同）；RealmRaid `fire`/`fire_again`/`ensure_lock` 是「在 2~3 个 target 间交替点」；只有 `check_refresh` / `screening_card` 循环 2 是「反复点同一个」。 |
| 2 | Verify 是否一样？ | **不一样。** 有「识别结果是 tuple」「`not appear(X)`」「`appear(X)`」「`appear(X)` 后 `not appear(X)`」「OCR 满足条件」五种。 |
| 3 | 下一次 action 前是否需要 fresh screenshot？ | **一致：需要。** 所有循环每轮开头都 `screenshot()`（`harvest_card` 是例外，但它不是 retry 循环）。 |
| 4 | target 是否必须重新识别？ | **不一致。** `RuleImage` / OCR / 动态列表 area：必须每次重 match / 重算；静态 `C_PARTITION_*` / `C_A_SELECT_CARD_LIST`：ROI 固定。 |
| 5 | 坐标是否应该重新计算？ | 对 `RuleImage` / OCR / 列表：是（`coord()` 读当前 `roi_front` / `area`）；对静态 `RuleClick`：每次 `coord()` 仍走 `ClickSampler.sample` 重采一个点，但 ROI 不变。 |
| 6 | 旧坐标能否安全复用？ | **一律不能假设可以。** 静态 ROI 恰好可以是巧合，公共层无从判断。 |
| 7 | retry interval 由谁控制？ | 现在是 `appear_then_click(interval=)` / `click(interval=)` 的 per-target `Timer`；语义是「这个 target 两次点击至少间隔 X」，不是「两次 attempt 间隔 X」。 |
| 8 | max_attempts 应由谁给？ | **调用方显式给。** 没有合理的项目级默认——`list_find` 用 10 / 3，Kekkai select-* 用 21，其它无。 |
| 9 | timeout 应由谁给？ | **调用方显式给**，且可能是多层（见 §9）。 |
| 10 | exhausted 后谁决定 Recovery？ | **Task。** 见 §8，每个案例都不同。 |
| 11 | exception 是否应该终止 retry？ | **应该透传**（见 §12）。当前代码里 `screenshot` / `appear` / `swipe` 抛异常都是直接向上，没有一处把它当「一次 verify 失败」吞掉。 |
| 12 | recognition failure 和 action failure 是否同一语义？ | **不是。** 「没识别到目标」（`find_one` 返回 `(None,None)`）走的是业务 Recovery（刷新 / break）；「点了但没进战斗」（`fire` 里 `I_RR_PERSON` 仍在）走的是继续 retry。混为一谈会让「列表到底了」被当成「点击失败」重试。 |

**差异集中在 Action 形态、Verify 形态、target 重定位、Recovery。共同的只有：
「每轮 fresh screenshot」「max_attempts 由调用方给」「异常透传」「exhausted 后 Task 决定
Recovery」。**

## 8. Recovery Boundary

| 案例 | Retry / 搜索 exhausted 后 | 观察 |
|---|---|---|
| `list_find` | `return False` | 最简：把结果交回调用方，调用方（`Orochi.check_layer` 等）自己决定 |
| Kekkai Utilize | `_record_utilize_failure`（失败计数 +1，满 3 → `set_next_run(+10min)` + `utilize_terminal_failure=True`）/ `_finish_low_value_utilize`（`set_next_run(+20min)`）/ `switch_friend_list` 换 fallback 分组 / `_card_not_found` → `raise TaskEnd` | 多层业务恢复：计数、延迟调度、换数据源、终止任务 |
| Kekkai Activation | `_card_not_found`（累计计数、切太鼓/斗鱼卡种、180min 后重试、`raise TaskEnd`）| 甚至会改配置（`card_type`） |
| RealmRaid | `when_attack_fail` 分支：`REFRESH` → `check_refresh()` → 成功 `continue` / 失败 `success=False; break`；`EXIT` → `break`；`CONTINUE` → 不特殊处理、靠 `find_one` 涂黑跳过失败格 | 恢复动作是「刷新列表 / 退出任务 / 屏蔽某格」 |

**Recovery 高度业务特化成立。** 长期边界：

```
公共 Retry primitive ──▶ RetryResult ──▶ Task 读结果决定 Recovery
```

**严禁**未来的 Retry primitive 自己调用：`goto_page` / `refresh` / `check_refresh` /
`raise TaskEnd` / `set_next_run` / `switch_friend_list` / `_card_not_found` / 选下一个
target / 改 config。primitive 的输出边界就是 `RetryResult`，到此为止。

（这与 D012 对 `frame_wait` 的边界完全一致：`frame_wait` 也是「返回结果，retry/recovery
是调用方的事」。）

## 9. Timeout / Attempts Contract

### `max_attempts` ≠ `timeout`

- **`max_attempts`**：最多执行 **Action** 几次。约束的是「动作次数」。
  例：`fire()` 最多点 3 次 partition。
- **`timeout`**：整个状态迁移最多允许持续多久。约束的是「墙钟时间」。
  例：`fire()` 从开始到进入战斗最多 8 秒。
- 两者**可同时存在**，任一先到即结束 retry。二者**都不允许项目级默认**——机制可以公共，
  数值必须调用方显式给（与 `frame_wait` 的「阈值必须显式传」同原则）。

### Timeout 的多层归属

| 层 | 归属 | 现有实现 | 例 |
|---|---|---|---|
| **Wait timeout** | wait primitive 自己 | `wait_until_appear(..., wait_time=)` / `wait_for_changed_and_stable(timeout=)` | 「等 `I_FIRE` 出现最多 3 秒」 |
| **Retry total timeout** | retry 机制（若未来存在） | 无 | 「点 partition 进战斗这整段最多 8 秒」 |
| **Business operation timeout** | Task | Kekkai `Timer(120)`（好友列表搜索）/ `Timer(20)`（切分组） | 「整个好友列表扫描最多 120 秒」 |

**禁止** `GLOBAL_ACTION_TIMEOUT = 3` 这类项目级万能数值——三个案例的合理 timeout 从
2 秒（`check_and_get_guild_rewards` 进度计时器）到 120 秒（好友列表搜索）跨两个数量级。

## 10. Fresh Screenshot Contract

**问题**：`Action` 执行后画面会变，`Verify` 必须读**动作后的新帧**，绝不能复用
`Action` 前的 `self.device.image`。

三种候选模式：

| 模式 | 描述 | 与现有代码的契合度 |
|---|---|---|
| A | retry primitive 每轮自动 `screenshot()` 再调 `verify` | 与 `wait_until_appear`（每轮自截）一致，但 primitive 就被绑死到 `BaseTask` / Device |
| B | `verify` callback 自己 `screenshot()` + recognize | 与 `list_find`（`self.screenshot(); target.image_appear(self.device.image)`）、`fire()`（`while` 开头 `screenshot()` 然后 `appear`）**完全一致**——现有代码本来就是这么写的 |
| C | 调用方传 `frame_provider`，primitive 取帧后传给 `verify` | 与 `frame_wait` 一致，但对 semantic verify 而言 `frame_provider` 多此一举（`verify` 里 `self.appear(X)` 本来就读 `self.device.image`） |

**推荐 B**：`verify` callback 拥有自己的截图 + 识别。retry primitive **不 screenshot**，
只负责「调 `action()` → 调 `verify()` → 计数 / 计时 / 返回结果」。理由：

1. 现有 `appear` / `wait_until_appear` / `list_find` / `fire` 全是「先 `screenshot()`
   再 `appear(...)`」的写法——B 是**零改造契合**。
2. primitive 不碰 Device / screenshot → 保持 `frame_wait` 同款的可注入、可单测、无环。
3. `verify` 是 `lambda: not self.appear(self.I_RR_PERSON)` 这类——它读 `self.device.image`，
   只要**调用方保证 `action()` 内部或 primitive 在 `action()` 与 `verify()` 之间刷新过帧**
   即可。最干净的约定是：**`action()` callback 负责在返回前留下一帧动作后的新截图**，
   或 primitive 约定「每次 `verify()` 前调用方注入的 `refresh()`」。→ 需要一条明确的
   长期契约（DECISION 候选 3）。

**必须防止的反模式**：`action()` 点完 → 不刷新帧 → `verify()` 读到动作前旧帧 →
「旧标识还在」→ 误判失败 → 多余 retry；或反过来「旧标识已不在（其实是旧帧本来就没截到）」
→ 误判成功。RealmRaid `fire()` 当前**没踩这个坑**（每轮 `while` 开头重截），但一个设计
不当的 retry primitive 很容易引入它。

## 11. Target Relocation Contract

Retry 时不能假设「第一次算出的 `(x, y)` 下次还有效」：

| target 类型 | 位置稳定性 | 每次 attempt 应该做什么 |
|---|---|---|
| 固定九宫格 `RuleClick`（`C_PARTITION_*`） | ROI 固定；`coord()` 仍每次重采落点 | `coord()` 重取（ROI 不变，落点变） |
| `RuleImage` | `match()` 后 `roi_front` 随命中位置改写 | **每次重新 `appear()` / `match()` 再 `coord()`** |
| `RuleOcr` | 文字框位置每次可能不同 | 每次重新 OCR 定位 |
| 动态列表 `area` | swipe 后必然变 | 每次 `find_everyone` 重识别 + 重设 `roi_front` |

**长期原则（DECISION 候选 2）**：公共 retry primitive **绝不缓存业务 target 坐标**。
每次 attempt 的「定位 + 动作」由 `action` callback 自己完成——callback 里写
`self.appear_then_click(X)` 或 `x,y = X.coord(); self.device.click(...)`，primitive 只
「调 callback」。

## 12. Exception Contract

现有三案例的异常处理现状：

| 现象 | 出现处 |
|---|---|
| 异常直接透传（无 try/except） | `list_find`（screenshot / finder / swipe 异常都透传）、RealmRaid 绝大多数循环、Kekkai 绝大多数循环 |
| `return False` | Verify 未命中 / 搜索耗尽（正常控制流，不是异常） |
| `raise TaskEnd` | Kekkai `_card_not_found` / RealmRaid 收尾 / 各失败终止路径 |
| `raise GameStuckError` | Kekkai `ocr_time()` OCR 结果为 0；上游 `stuck_record` |
| `raise GamePageUnknownError` | `goto_page` 超时、`switch_friend_list` 超时 |
| timeout 返回结果不抛 | `frame_wait`（D012 明确）、`wait_until_appear(wait_time=)` 返回 `False` |

**公共 primitive 默认：未知 Action / Verify 异常直接透传。** 理由：

- 项目没有「可重试异常白名单」的统一约定；`module/base/retry.py` 的 `@retry` 有
  `exceptions=` 参数，但那是基础设施层（adb 断连等）的显式选择，task 层无此先例。
- 把真正的代码 bug（`AttributeError` / `KeyError` / `None + datetime`）静默当成「一次
  verify 失败」重试，会**掩盖缺陷**——RealmRaid `medal_fire` 的 `medal_grid=None` /
  Kekkai `ocr_time` 的 `None + datetime` 正是这类，应该崩出来被发现，不是被吞。
- 「让调用方定义可重试异常」是未来的**显式能力**，需要单独讨论，本轮不实现。

## 13. Pattern Catalog

### Pattern A —— Semantic Transition

```
State A ──Action──▶ 期望 State B ──▶ wait 语义标识（正向出现 / 旧的消失 / 两者兼有）
```

Owner：**Task**（组合既有 `wait_until_appear` / `wait_until_disappear` / `appear`）。

真实候选：
- RealmRaid `fire()`：`click(partition)` → 期望 `I_FIRE`（S1，当前缺）
- RealmRaid `fire()`：`click(I_FIRE)` → 期望战斗页（当前 S2 弱验证 → 应升级 S3）
- Kekkai `run_activation` A6：点激活 → 期望 `I_A_INVITE`（有等待、缺 timeout）
- Kekkai `screening_card`：点目标 → 期望 `I_A_EMPTY` 消失（S2）

### Pattern B —— Structural Transition

```
baseline ──Action──▶ changed ──▶ stable
```

Owner：**`module/base/frame_wait.py`（已存在，无缺口）**。

真实候选：`list_find` 翻页、KA `check_card_num` 翻页、KU `perform_swipe_action`。
缺的是 Level C 参数 + 调用方 baseline 捕获，不是 primitive。

### Pattern C —— Bounded Semantic Retry

```
attempt 循环（bounded by max_attempts AND/OR total timeout）:
    action()          # 调用方 callback：自己定位 + 动作，留下动作后新帧
    if verify():      # 调用方 callback：读新帧判断业务结果
        return RetryResult(success=True, attempts=n, elapsed=t)
return RetryResult(success=False, timed_out=?, attempts=n, elapsed=t)
```

Owner（若未来抽）：**新的极小 primitive（仅循环 + 计数 + 计时 + frozen result）**；
`verify` / `locate` / `action` / `recovery` 全在 callback / Task。

真实候选（**当前全部无 bound，接入是 Level C**）：RealmRaid `fire` / `fire_again` /
`ensure_lock` / `check_refresh`；Kekkai `screening_card` 各层。

### Pattern D —— Business Recovery

```
RetryResult / 搜索结果 ──▶ Task 决定：refresh / continue / skip / fallback / switch group /
                                        back / set_next_run / raise TaskEnd
```

Owner：**Task，永远。**

### Pattern E —— 已有的可靠有界循环

```
for _ in range(N):  /  while not Timer(T).reached():
    screenshot(); if appear(明确标识): ...
```

真实例子：`list_find`（`range(max_swipe)`）、Kekkai `_current_select_best` /
`_select_lazy_*` / `_reselect_*`（`range(21)` + `Timer(120)`）、`switch_friend_list`
（`Timer(20)`）、`check_box_ap_or_exp`（`Timer(6/12)`）、`goto_page`（`Timer(30)`）、
GeneralBattle Page FSM（`battle_timer` / `_tick_timeout`）。

**原则：不为了「统一到某个新框架」重写这些。** 它们已经有界、有语义确认、经过实战。

## 15. BehaviorTrace Future Events

v1 只有 `ACTION` / `TASK`（D004），且**明确不记录** `appear()` / OCR / `Timer.reached()` /
每个 while tick。未来候选：`RETRY` / `VERIFY` / `WAIT` / `TIMEOUT` / `RECOVERY` /
`TRANSITION`。

基于三案例的**主要失败模式**（都是「弱 / 缺 Verify + 无界循环」）排优先级：

| 事件 | 能回答什么 | 数据量 | 优先级 |
|---|---|---|---|
| **`RETRY`** | 「哪个 target / 哪段状态迁移经常需要 ≥2 次尝试 / 经常 timeout」——**直接指向可靠性最差的点**。一次完整 retry 循环记一条（target/transition 名、attempts、elapsed、outcome=success/timed_out），天然包含 timeout 信号。 | 低（每次迁移 1 条） | **最高** |
| `VERIFY` | 「action 后 ExpectedState 成没成」——更细，但每次 attempt 一条会很吵，且违背 D004「不记录 appear()」的克制原则 | 高 | 中 |
| `TIMEOUT` | 「哪些状态最容易卡」——是 `RETRY` 的 `timed_out=True` 子集，单独设意义不大 | 低 | 低（并入 `RETRY`） |
| `WAIT` / `TRANSITION` | 更适合等有真正的 State 层之后再说 | — | 低 |

**推荐：下一步观测能力做 `RETRY` 事件**（一次 bounded retry 循环结束记一条）。前提是先有
retry primitive 或至少有统一的 retry 调用点——所以它排在 retry 抽象之后。**本轮不改
BehaviorTrace。**

## 17. 是否抽公共层

**PARTIAL —— 且不是现在。**

### 明确不抽（现在不需要）

- **structural wait**：`frame_wait` 已就位，无缺口。
- **semantic verify**：`wait_until_appear` / `wait_until_disappear` / `appear` 组合已足够；
  `wait_until_disappear` 补 `wait_time` 是 1 行签名扩展，不是新类，且改动本身 Level C。
- **`Verifier` / `ActionVerifier` / `GenericTargetLocator` / `RecoveryEngine` /
  `GenericStateMachine`**：三案例证明 Verify 形态、target 重定位、Recovery **差异都很大**，
  硬抽会逼业务扭曲。

### 唯一可能值得抽的一小层（未来，非本轮）

只有**「bounded retry 内核」**——`retry_until(action, verify, *, max_attempts, timeout)
-> RetryResult`：

- **只**负责：循环、计 `attempts`、按注入 `clock` 计 `elapsed`、`max_attempts` / `timeout`
  任一到即停、返回 frozen `RetryResult`。
- **不**负责：locate（在 `action` callback）、verify 逻辑（在 `verify` callback）、
  screenshot（callback 自己截，模式 B）、recovery（Task 读 `RetryResult` 决定）、
  target 类型理解、异常吞咽（默认透传）。
- 形态参照 `frame_wait`：`module/base/` 下、依赖可注入、frozen result、`timeout` 必须为正
  不允许 `None`、超时不抛。

### 为什么「不是现在」

1. **每个真实消费者的接入都是 Level C**（当前全部无 bound，加 bound 改时序）——现在写
   出来就是零消费者组件，会像 `frame_wait` 一样长期悬空，且**没有一个真实 adoption 来
   校准它的形状**（`action` 每轮多 target 交替、`verify` 五种形态——对着三个假想需求设计
   容易设计歪）。
2. **项目优先级 `correctness > reliability > observability > abstraction`**：§16 的
   correctness / dead-code 队列是**现在就能做、零真机、低风险**的净收益；retry 内核是
   abstraction，排在最后。
3. **主线保持单一**（ROADMAP 纪律）：这一轮的产出是「决策 + 队列」，不应同时启动 retry
   实现。
4. retry 内核只有约 15 行——完全可以等**第一个真实 Level C 迁移**（大概率是 RealmRaid
   `fire()`）时，对着那个真实消费者顺手抽出来，比现在凭空造更准。

### API proposal（仅供未来参考，本轮不实现、不接消费者）

```
retry_until(
    action:  Callable[[], None],          # 每次 attempt 调一次；内部自己 locate + 动作 +
                                          # 留下动作后新帧（或由 caller 保证 verify 前帧已刷新）
    verify:  Callable[[], bool],           # 读当前帧判断业务结果；True = 成功
    *,
    max_attempts: int,                     # 必填，无默认；<1 抛 ValueError
    timeout: float,                        # 必填，正数，无默认；不允许 None/inf；超时不抛
    clock:   Callable[[], float] = time.monotonic,
    on_attempt: Callable[[int], None] | None = None,   # 可选：每次 attempt 前回调（未来接 RETRY trace）
) -> RetryResult

@dataclass(frozen=True)
class RetryResult:
    success: bool          # verify() 曾返回 True
    timed_out: bool        # 因 timeout 结束（而非 max_attempts 用尽）
    attempts: int          # action() 实际执行次数
    elapsed: float         # 按注入 clock，秒
    last_verify: bool      # 最后一次 verify() 的返回值
```

- **异常策略**：`action` / `verify` 抛出的异常**原样透传**，不计入 attempt、不当 verify 失败。
- **screenshot 所有权**：primitive 不 screenshot；`action` / `verify` callback 负责（模式 B）。
- **无 recovery**：`success=False` 时 primitive 只返回，`goto_page` / `refresh` /
  `raise TaskEnd` 一律由 Task 读 `RetryResult` 后自己做。

## 18. 下一阶段推荐

**推荐 Option 2 —— 先执行一轮纯 Level A correctness / dead-code cleanup（§16 队列）。**

### 为什么选它

- §16 里有**确定的、零真机、低风险**的净收益：不可达 `return` + 死分支、`None + datetime`
  会崩、stdlib 随机源不一致、死代码（`medal_fire` / `is_ticket` / `medal_grid` /
  `AttackNumber` / `parse_rule` / `last_best_index`）、lazy_roll 语义误用。
- 项目优先级 `correctness > reliability > observability > abstraction`——cleanup 是
  correctness，排第一。
- 每一项都能配 characterization 测试锁「改动前后行为等价」（死代码删除 = 全仓 grep 零调用方
  已验证；不可达 `return` 删除 = 行为完全不变；随机源换 helper = 分布等价）。
- 三个 characterization 测试文件（`test_list_find` / `test_kekkai_*_state` /
  `test_realm_raid_state`）已经把现状锁死，cleanup 会有明确的回归护栏。

### 为什么暂时不选另外三个

- **Option 1（实现 bounded retry primitive）**：形状已知但**零真实 adoption 可校准**，
  每个消费者接入都是 Level C；现在写 = 又一个悬空组件。等第一个真实迁移时抽更准。
- **Option 3（第四个业务案例）**：三个案例（`list_find` 纯 structural、Kekkai 两类混合、
  RealmRaid 纯 semantic + 深度耦合 GeneralBattle）**已经覆盖了足够不同的形态**，第四个
  大概率只是重复已有结论，边际收益低。
- **Option 4（主线冻结等 Level C）**：不成立——§16 有一整队 Level A 工作可做，主线没到
  「只剩真机活」的程度。

## 附：§39 十四问速答

1. **FrameWait 只负责**：按注入 `frame_provider` 反复取帧喂给内部 `FrameStateDetector`，
   按注入 `clock` 计时，到 `timeout` 停；返回 `FrameWaitResult`。不做 retry / recovery /
   换动作 / 业务阈值 / 自截。
2. **Semantic wait 负责**：等某个业务 `I_*` / OCR 条件出现或消失，在有限 `wait_time` 内。
   现有 `wait_until_appear` / `wait_until_disappear` / `appear` 承担。
3. **Verify 是否需要新公共 abstraction**：**否**。现有 primitive 组合足够；差异太大不宜抽类。
4. **Retry 是否已值得抽**：**PARTIAL——只有 bounded 内核值得，且不是现在**（零真实 adoption、
   接入全是 Level C、优先级低于 cleanup）。
5. **如果抽，只应抽哪一小层**：`retry_until(action, verify, *, max_attempts, timeout) ->
   RetryResult(frozen)`——只有循环 + 计数 + 计时 + 结果。verify / locate / recovery /
   screenshot / 异常吞咽都不进去。
6. **Recovery 为什么留在 Task**：三案例的失败后动作是 `refresh` / `switch group` /
   `set_next_run(+10/20/180min)` / 改 config / `raise TaskEnd` / `find_one` 涂黑——
   完全业务特化，没有公共形态。
7. **Timeout 与 max_attempts 的区别**：`max_attempts` 限「Action 执行次数」；`timeout` 限
   「整段迁移的墙钟时间」。可同时存在，任一先到即止，数值都必须调用方给（无项目默认）。
8. **Action 后 fresh screenshot 谁负责**：`verify` / `action` callback（模式 B）——与现有
   `screenshot(); appear(...)` 写法零改造契合。retry primitive 不 screenshot。
9. **Retry 时 target 是否必须重新定位**：`RuleImage` / OCR / 动态列表——**必须**每次重
   `appear` / `find_everyone` / 重算；静态 `RuleClick`——ROI 不变但 `coord()` 仍重采落点。
10. **Retry primitive 是否允许缓存旧坐标**：**绝不**。每次 attempt 的定位 + 动作在
    `action` callback，primitive 只调 callback。
11. **Exception 默认透传还是吞掉**：**透传**。吞掉会把 `AttributeError` / `None+datetime`
    这类真 bug 伪装成「retry 失败」。可重试异常白名单是未来显式能力。
12. **BehaviorTrace 下一步最值得新增**：**`RETRY`**（一次 bounded retry 循环结束记一条，
    带 attempts + outcome，天然含 timeout 信号），排在 retry 抽象之后。
13. **纯 Level A correctness 问题**：见 §16——RealmRaid 不可达 `return` + 死分支、
    `ocr_time` 的 `None+datetime`、KA `check_card_num` stdlib 随机、KU lazy_roll 语义误用、
    死代码 `medal_fire`/`is_ticket`/`medal_grid`/`AttackNumber`/`parse_rule`/`last_best_index`。
14. **下一阶段唯一推荐任务**：**Option 2 —— Level A correctness / dead-code cleanup**
    （逐项配 characterization 回归护栏，生产行为等价，不接 retry 实现）。
