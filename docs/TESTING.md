# 验证规则

> 统一告诉所有开发 AI：改完代码以后到底怎么验证。
> 本文档只保存**长期通用验证规则**（最后核对：2026-11-27）。一次性测试数字放任务交接/日志，单任务测试桩细则放对应 `tests/test_*.py` docstring；历史专项测试口径原文（`5.a ~ 5.ae` 及 L1/L2 细则）见 [TESTING_case_notes_2026-09_11.md](archive/TESTING_case_notes_2026-09_11.md)。
> 更新触发：测试命令、验证分级、真机限制、守护规范或长期测试原则变化。

---

## 1. 按风险选择最小验证（D069，2026-11-12生效；2026-11-27收紧）

本节替代“任何源码修改都必须全量全绿”的旧默认。验证回答本次实际问题，不用测试数量代替可用性，不以耗尽额度换取离线覆盖。

| 改动 | 默认验证 |
|---|---|
| 文档、规则、Skill | 链接/引用、规则一致性、编码及本轮 diff；不跑 unittest、compileall 或业务场景 |
| 图片/ROI/OCR 规则 | 原始画面、JSON/生成属性/尺寸配套，必要时一次实际原图匹配；不自动跑整套业务测试 |
| 局部业务源码 | 从真实故障选最小相关方法/类，必要时少量回归；只编译改动文件，再查本轮 diff |
| 共享核心/跨模块 | 先列直接影响的契约与代表性调用方，选择相应检查；需要长测时说明范围、预计耗时和实测仍缺什么，不自动全量 |

### 1.1 时间与范围预算（2026-11-27收紧）

- **收口原则**：仅审查本次增量及直接调用方，验证批准行为和直接回归风险；默认不新增测试文件或复杂替身，优先复用最小现有用例。发现范围外缺陷只记录并报告，不顺带修复、重构或扩大验证；确需扩大修改范围先交用户确认。最小检查满足后停止离线扩测，交付待实测版本。
- 游戏流程改动默认只做改动文件编译、本轮 diff 检查及 **1～3 个**最能区分对错的离线场景，优先真实故障、正常路径和高风险动作。不是每个函数/分支各写 1～3 项，不默认整类/整模块回归。
- 普通任务阶段离线测试累计默认 **120 秒**，包含执行者首测、修正复测及 Codex 复核；按守护日志的墙钟耗时累计，不因拆组、换执行者或新会话重置。日志缺失先核对已有运行记录，不再默认获得完整预算；额度无法确认时报告不确定，不擅自扩测。耗时上限是资源保护，不代表必须跑满。
- 沿用 `toolkit/python.exe dev_tools/guarded_unittest.py --timeout-s <本次上限> -- tests.<模块>.<类>.<方法>`；本次上限不得超过阶段剩余预算。解释器、内存/日志限制、停止信号及 14/16 核 PID 规则不变。预算耗尽保留结果并停止自动扩测；更大任务需要扩大预算时说明理由并由用户批准。
- 不为建立基线先跑 discover。复用内容未受影响且可核实的现有命令/日志/快照证据；失败后只复跑失败及直接受影响项，不默认重复执行者测试组。普通局部分支修复不触发新一轮整组回归。
- 保留现有测试，不批量删除。新增用例只锁真实故障或稳定契约；不按分支机械堆 mock，不为凑覆盖率搭复杂假游戏世界。确需复杂替身时，先说明其能发现的真实风险及与现场的对应关系。不得为了测试替身兼容在生产代码增加吞异常、无预算重试或重复动作的兜底。

### 1.2 全量是显式项目，不是默认门禁

- 只有用户明确要求，或当前已批准验收合同明确包含该次全量，才执行 `toolkit/python.exe dev_tools/guarded_unittest.py --profile full -- discover -s tests`。单纯“实现/修复功能”、共享核心改动、旧模板泛写“全量”，均不自动授权。
- 一个批准阶段默认最多一次；局部复修后默认针对性复验，不为刷绿反复全量。已有明确的范围/时点/次数授权直接沿用，不重复问。
- 未获全量授权时，先完成已授权的局部工作，报告“本次未运行全量”，不能把它当失败门槛阻止交付，也不能宣称全系统通过。正式验收合同若确有全量门禁，则如实保留待验状态。

### 1.3 实测、交付与审查

- 游戏/UI 问题先核对原始截图、失败日志和真实调用链。已有明确实机授权时优先最短正常路径及本次故障路径；没有授权不启动设备/服务，最小离线检查后尽早交付“待实测版本”、具体预期、最短步骤和失败留证要求，不继续堆 mock 代替实测。
- 批准范围内已知误拖、死循环等明确缺陷先修；范围外缺陷只记录并报告，未经确认不顺带修复。不以尽早实测为由把本次已知错误推给用户碰运气。临场识别率、动画与游戏机制不确定性单列待验，不能通过假定规则的替身测试宣称已经解决。
- 开发角色统一称执行者，不绑定模型或客户端。开发结果由 Codex 审查真实增量和关键调用链，执行必要的最小测试后给出验收结论；Codex 复核与执行者共享阶段预算，不默认重跑已有测试组。用户授权 Codex 直接实施时单列自审与验证，不冒称外部独立审查。
- 测试失败按实际行为和风险判断；本次批准范围内已知核心行为缺陷须处理，范围外问题及无关或仅告警断言失败如实保留，不因此扩大整个任务回归，也不删除断言刷绿。
- 报告写清代码改动、关键行为及证据、尚未验证部分、阶段累计测试耗时与剩余预算。以现场效果为主，不以通过数量为主要结论；离线/mock/同源截图命中不等于实际可用。实机未验证时明示“待实测”，给出下一次最短验证路径。
- `git diff --check` 预存问题与本轮问题分开；CRLF 提示不是错误，不为全仓变绿改无关 WIP，不额外引入测试/lint 工具。

## 2. 测试分级

| 级别 | 含义 | 典型改动 | 本轮能否自证 |
|---|---|---|---|
| **Level A：纯静态 / 单元测试** | 逻辑可被 mock + 断言完全覆盖，不依赖真实设备 / 页面 / OCR | BehaviorTrace、纯图像 / 状态 detector、Config 字段、死代码删除、API 参数契约、纯函数、异常隔离 | 是 |
| **Level B：集成逻辑测试** | 跨多个模块的控制流，仍可用 mock 驱动，但要拼装较多依赖 | `Script.run` 出口语义、`Control.swipe` 后端分发、`flush_area_cache` 分支、通用战斗 FSM 的 handler 分派 | 是（用 `__new__` + `SimpleNamespace` / `Mock` 拼装） |
| **Level C：MuMu / 游戏内真机** | 必须连真实模拟器 / 游戏 / OCR 服务才能验证 | 列表滚动距离阈值、minitouch 真实时序变化、RealmRaid / RyouToppa 页面流程、Kekkai 滑动与稳定判定、GeneralBattle 实际行为变化、任何改变真实滑动 / 点击时序的改动 | **否**——需要用户明确授权并提供真机窗口 |

**归级原则**：如果一个改动「在 minitouch / adb / uiautomator2 等真实后端上的可观测行为可能变化，且无法用单元测试证明不变」，它就是 Level C，本轮不做，记入 `docs/ROADMAP.md` 的「需要真机验证的任务」区。

## 3. 当前禁止事项（无用户明确授权时）

- 不启动 MuMu / 任何模拟器。
- 不启动游戏客户端。
- 不连接真实 ADB 设备。
- 不运行需要真实 Image / OCR RPC 服务的流程（`tests/` 内离线用例已用 mock，不要另跑 `script.py` / 各 `script_task.py` 的 `__main__`）。
- 不执行 `dev_tools/` 下需要设备的脚本。

## 4. Git 规则

默认（无用户明确要求时）：

- 不 `git commit` / `git push` / `git merge --continue` / `git rebase --continue`。
- 不 `git reset --hard` / `git checkout --` / `clean` / `stash` 丢弃他人或预存 WIP。
- 当前分支 `master`，实时状态以 `git status` / `git rev-parse HEAD` 为准；工作区长期处于「多轮改动未提交」状态是有意的。

## 5. 测试失败与新增测试的通用原则

- **不为了让测试变绿而修改无关业务代码**：测试红了先定位根因。
- **区分本轮与既有失败**：用相关内容基线和最小复现对照，不默认前后两次 discover；既有失败单独报告，不顺手改。
- **新增测试必须真实锁住修复语义**：
  - correctness Bug 尽量做**正向 + 反向验证**——修复后通过，临时回退修复后失败（验证后必须恢复）；
  - API 契约测试要断言「谁被调用、带什么参数」，不只是「没抛异常」。
- **配置与 i18n 护栏**：
  - 新增/改动配置模型时核对标量参数展开、默认值与只读性（`tests/test_config_model_script_task.py`）；测试里临时切目录时，`os.chdir` 必须放在所有项目 import **之后**（`module/logger.py` 与 `deploy/logger.py` import 时会 chdir 回仓库根）。
  - 改动 `assets/i18n/zh-CN.json` 时只能按原格式追加、不得整体重新序列化（存在历史重复键）。
- **不允许挂死测试与脆弱时序断言**：可能进入循环等待的路径必须带哨兵异常或次数上限；性能/吞吐只用极宽松 `assertLess` 防数量级异常；`mock` 只作局部逻辑证据，不替代实测。
- **真实 OCR 回归边界**：含进程内 OCR 模型的重型用例（如 `OAS_REAL_OCR_TESTS=1`）默认 skip 时必须封死默认 RPC 路径并在报告注明未执行，禁止宣称已离线全覆盖。
- **D073 口径**：单任务 / 单缺陷的测试替身构造、夹具约束与回归范围说明直接写进对应 `tests/test_*.py` 模块头 docstring，不再向本节堆叠单任务条目。

### 5.1 受守护的测试运行入口与循环哨兵（D056，原 §5.ac）

分组与全量回归统一通过受守护入口 `dev_tools/guarded_unittest.py` 执行（`psutil` 监控在被测进程之外）：

```text
# 普通任务阶段累计 120 秒；复测/复核须扣减剩余预算（守护默认内存上限 3 GiB）
toolkit/python.exe dev_tools/guarded_unittest.py --timeout-s 120 -- tests.test_a tests.test_b
# 仅明确批准该次全量时（profile 默认 900s / 3 GiB）：
toolkit/python.exe dev_tools/guarded_unittest.py --profile full -- discover -s tests
```

- **内存与清理口径**：统计测试进程及其全部后代的 Windows 私人提交（`PrivateUsage`）；只清理自己启动并跟踪的进程树（PID + 创建时间校验），不碰无关 OAS 进程。
- **互斥锁与退出码**：`log/test_runs/guarded_unittest.mutex`（OS 文件锁）与 `guarded_unittest.lock`（JSON 运行记录）保证同工作区同时仅跑一份；退出码 `0` 通过、`1` 失败、`2` 参数/环境不可用、`10` 超时、`11` 内存超限、`12` 中断、`13` 守护异常、`14` 已有运行拒绝、`15` 日志超限、`16` **清理失败**（绝不报通过，且不删运行记录，须人工核对残余 PID）。
- **循环测试自带次数哨兵**：驱动 `while 1` 之类循环时，高频边界（`screenshot` / `appear`）使用带次数上限的普通函数，超限直接抛含用例名与阶段信息的 `AssertionError`；纯高频边界不用 `Mock` 记录调用历史防内存暴涨；使用虚拟时钟时等待动作须推进时钟。

## 6. 测试文件组织

- 目录：`tests/`，`unittest` 风格，文件名 `test_*.py`。
- 一个特性 / 一个修复对应一个测试模块，模块 docstring 说明背景、锁定的契约与证据边界（含与真机 Level C 的区别）。
- 需要清理进程内单例（`BehaviorTrace` / `FatigueManager`）的用例在 `setUp` / `tearDown` 调对应 `reset_*`。
- 需要隔离文件系统的用 `tempfile.TemporaryDirectory` + monkeypatch，不碰真实 `log/` / `config/`。

## 7. 收尾（每轮开发 / 正式设计结束前）

```text
工作完成
 → 按 §1 执行本轮已选择/批准的最小验证，不默认全量
 → 人工核对 git diff / git status（无误改、无调试残留、无范围外触碰）
 → 按 D073 审查 6 份项目文档：只更新项目事实真正发生变化的文档（普通修复默认只写 DEVELOP_LOG + 必要时 ROADMAP 1 行）
 → 再次 git diff --check
 → 输出报告（含固定的「## 文档同步」段）
```

## 8. OAS Architect Skill 与任务接力的验证

### 8.1 静态与范围验证

Skill / 入口 / 状态文档变更检查 frontmatter、角色路由、references、文档链接、CURRENT、共同核心、编码、任务增量及 WIP 保护。使用仓库外针对性检查验证辅助脚本，记录命令、环境、输入快照、结果和证据位置。业务变更按 §1 / §5.1 守护，Level C 按 §2。

### 8.2 普通恢复与角色行为

普通恢复先确认 Git、CURRENT、批准范围和下一步，必要模块资料按任务补充。12000 Unicode 字符是提醒，预计不足和超过提醒值继续补齐必要信息。已知量与估算分别说明，精确宿主量会后审计。

场景覆盖前置记忆偏大、旧 `remaining` 参数、Windows 首读 / UTF8 重试、CURRENT 缺失、未知字段、切换其他业务任务、六种角色、接管停写和角色权限边界。核心通过条件为必要事实已恢复、真实缺口说明、批准范围与 WIP 保护。自审、受控回放和独立客户端分别记录。

### 8.3 明确触发的严格验收

代码验收核需求、实现、差异、适用测试和证据。读取预算等专项验收先明确合同、版本和范围，再用原始 JSONL 会后审计，按 `call_id` 配对，包含发现 / 错误 / 警告 / 包装，未知 / 缺失 / 重复 / 截断保留。具体历史预算及源 / 正文摘要、范围和接收协议见 [review-closeout](../.agents/skills/oas-architect/references/review-closeout.md)。旧 T12 结果按旧合同保存，新普通恢复单独判定。

READONLY-V1 仅用于合同 `execution_mode` 为 `readonly_audit` 的专项审计，要求仅 Read / Glob / Grep，禁用写入、代码执行、hooks 和 MCP 等副作用通道，任何写入尝试即 FAIL。保留实际工具集合、调用配对、输入和前后 SHA，退出 0 单独不能证明通过。

### 8.4 证据与收尾

静态 / 隔离通过按对应内容快照记录，相关内容变化使证据过期。真实客户端发现、角色行为和协作需要实际新会话证据，缺条件标 BLOCKED，T9 保持 NOT_TESTED。逐项检查六份文档并按事实同步，原始日志 / 报告 / 基线和预存业务 WIP 受保护。Phase5 按用户明确批准进入。
